# Scale Out With Cloudflare

**Design proposal · spike baseline `173bc712d` · November 2026**

An operator enables Cloudflare once. Bifrost then provisions and maintains two demand-driven external scopes in its existing worker pool. Cloudflare Workers takes approved Python workflows and Cloudflare Containers takes qualified Linux overflow. The VM primary remains the warm floor and the trusted execution path. “Region:earth” means Cloudflare can supply eligible capacity without the operator running a Kubernetes fleet for it. Bifrost retains the database, control plane, protected workloads, and final authority over every claim.

Use upstream's [capacity provider core and conformance contract](https://github.com/gobifrost/bifrost/pull/1423), [API-owned execution and remote control](https://github.com/gobifrost/bifrost/pull/1424), and [Containers provider lifecycle](https://github.com/gobifrost/bifrost/pull/1425). Each launcher registers as an `external` worker. Reuse the prepare/start/observe/release state machine, the signed control WebSocket, and the existing queue, lease fences and terminal ACKs. Use ordinary Workers, Durable Objects and Containers. Workers for Platforms is excluded.

## Operator Experience

1. In **Settings → Capacity → Scale Out With Cloudflare**, choose **Connect Cloudflare**. A platform administrator supplies the account ID and a write-only, account-restricted API token. Bifrost checks the account, permissions it can verify, entitlements and available capacity. Show provider prerequisites and the exact account that will receive resources before enabling.
2. Choose **Managed Tunnel** or **Existing HTTPS Endpoint**. Managed Tunnel asks for one zone and a new dedicated hostname and checks whether the installation has the managed connector. Existing HTTPS Endpoint asks for a dedicated worker ingress URL and probes its TLS and WebSocket behavior. Show which methods and route families will be reachable and whether existing Access or mTLS requirements can be met.
3. Review **Capacity Limits**, **Monthly Spend Limit**, and **Workload Placement**. Show the shared pool limit, VM floor and ceiling, Workers launcher and slot limits, Containers instance limit and size, and per-scope work kinds. Display a conservative cost estimate and validate that the shared limit leaves room above the VM ceiling. Suggested pilot preset is one Workers launcher with two slots and one Container with one workflow slot where the instance size and workload fit, both with zero warm instances. The operator sets the spend limit before enabling. Approved Normal workflows and explicitly eligible Linux workflows are the initial policies when both scopes are selected. Additional work kinds require an explicit policy and a qualified runtime capability.
4. Press **Scale Out With Cloudflare**. The shared PlatformJob shows provision, connectivity check, signed hello, and admission activation. **Capacity** shows each scope's desired, reserved, starting, ready, busy, draining and unconfirmed counts, available slots, queue age, last successful hello/probe, deployment revision, cap or budget hold, approval counts, and **Estimated Spend** with its period, timestamp and data freshness. Show **Cleanup Pending** or **Action Required** with the owning resource and next remedy. Refresh from the existing capacity resource on load, reconnect and existing notification invalidations.
5. **Scale In** closes cloud admission immediately and drains cloud capacity to zero. It retains the connection, validated policy and provisioned resources, and shows any continuing charges. **Scale Out With Cloudflare** resumes that installation. **Disconnect** requests full teardown, automatically draining first if needed. Keep the token and the remaining-resource inventory until deletion is verified. A replacement token can resume a blocked disconnect. Once verified, remove credential material and retain an audit receipt. Operator revocation at Cloudflare follows the receipt.

## Reachability and Credentials

| Option | Trade-off | Decision |
| --- | --- | --- |
| Bifrost-managed `cloudflared` | Outbound-only connector from Bifrost, public dedicated hostname with a narrow ingress and a catch-all 404. Requires a Cloudflare-managed DNS zone and a supervised connector. | Recommended default on supported installations. Package a pinned connector with the install lifecycle, dormant by default, with a local supervisor and private token injection. Shared deployments can run replicas of the same tunnel. The API never needs a Docker socket or cluster-admin credentials to start it. [Tunnel setup](https://developers.cloudflare.com/tunnel/get-started/) |
| Existing public HTTPS | No tunnel or DNS writes. An existing reverse proxy must provide the same narrow ingress, support long-lived WebSockets and use verified TLS. | Supported alternative and first delivery slice. Validate it from a Cloudflare canary, including expected refusals for unrelated routes. Require the configured origin and reject redirects. |
| Cloudflare Access or mTLS | Adds perimeter identity, certificate/service credential lifecycle and another dependency on reconnect. Access service tokens would add a standing shared secret to compute unless a separate short-lived compatible design is qualified. Workers mTLS bindings have proxied-zone restrictions and the Linux launcher needs its own compatible transport. | Leave managed Access/mTLS outside initial delivery. Qualify authenticated WebSocket, refresh and scoped SDK calls for both runtimes before supporting a mandatory perimeter policy. [Access mTLS](https://developers.cloudflare.com/cloudflare-one/access-controls/service-credentials/mutual-tls-authentication/) · [Workers mTLS binding](https://developers.cloudflare.com/workers/runtime-apis/bindings/mtls/) |

The ingress entry point allows the worker-control upgrade and the minimum method/path families for the selected runtime's source, package, SDK, logging and refresh contracts. Derive and review that matrix from the launcher and hosted harness. Enforce it at the dedicated local ingress proxy as well as the tunnel, with body limits and rate controls before expensive work. Login, OpenAPI, admin routes and test stub routes are excluded. The signed, nonce- and generation-fenced hello authenticates an incarnation over TLS, with exact reservation UID, scope, version and profile checks. Scoped run credentials continue to enforce the original caller's reach at each SDK operation. Tunnel and perimeter controls cannot grant workload authority.

**Change required from the spike.** Both hosted capacity providers currently use a `CAPACITY_TOKEN` Worker binding. Bifrost must keep the capacity token and derivation root local, along with `BIFROST_SECRET_KEY`, DB credentials, and the Cloudflare API token. Add a signed transport adapter to the existing capacity API for managed Cloudflare scopes. A private signing key stays in Bifrost and the provider receives only its public verifier. Sign canonical method, audience (installation, scope and generation), path, body digest, nonce and short expiry, and enforce freshness and replay checks with bounded storage. Reuse exact reservation identity for idempotency. Legacy VM capacity auth stays on its existing contract. Qualify this change against the upstream capacity conformance suite.

Reserve an incarnation in PostgreSQL and allocate and journal its immutable resource UID before contacting the managed provider. Adapt prepare to accept that UID and the derived control key, bound to the signed request. The ledger rejects mismatches and starts only the committed identity. Observe before retrying an ambiguous operation. Workers deliver the key to the launcher over the private DO binding. Containers inject it into the non-root supervisor and strip it from children, with the spike's process-environment protections. A launcher or Container gets only its incarnation's derived control key and the existing short-lived run- or attempt-scoped credentials needed for authorized API calls. Capacity API responses, artifacts, telemetry and errors exclude key bytes. Require finite startup, reconnect and lifetime limits, plus bounded remote runtime leases. Renew leases only when Bifrost has fresh provisioning-credential health and active admission or drain authority. Expiry stops new work, reconnect loops and local processes, while retained terminal receipts remain available within a bounded recovery window.

Store the Cloudflare API token and Bifrost-side signing/derivation keys in versioned encrypted platform credential records using the existing platform secret encryption service. Connection state and job payloads carry references only. Keep the connector token local to the supervisor, stored encrypted for restart and passed by protected file or equivalent private channel. Limit decryption to trusted Bifrost services by role and purpose. Audit connection, token version changes and access failures without credential values. The token rotates by validating a replacement against the same account and zone, then atomically switching credential versions and invalidating old clients. Resume any in-progress operation by readback before the next mutation. Users revoke the previous token after rotation is verified. API-token rotation does not rotate launcher identity. Signing-key rotation adds the new public verifier before switching signers, then retires the old verifier. Derivation-root rotation uses a new generation and drains incarnations tied to the old key.

## Provisioning and Cloudflare API Coverage

The enable job reproduces the hosted harness's resource operations. It checks the account and owned names and the spend guard, validates deployment inputs, deploys private dependencies then providers, prepares the pinned image and application, configures the tunnel/connector/DNS when selected, and proves reachability and signed readiness before admitting work. It records readback for each step. The manual test launcher, model-stub Workers, local debug stack, scratch handoffs and immediate reset deployment in [the Phase 7 harness](../e2e/README.md#phase-7-hosted-three-scope-qualification) are qualification tools. The managed product replaces the private credential handoffs with its Bifrost-side controller.

**Minimum credential envelope.** Restrict **Workers Scripts Write** to the selected account for upload, version/deployment, settings, bindings and owned deletion. Add the account's **Workers Containers Write** (Containers Write in the permission catalog) only for Containers app and registry operations. Use **Cloudflare Tunnel Write** on that account and **DNS Write** for the selected zone only for managed reachability. Require a zone ID to avoid needing account-wide discovery. Readback uses those grants where accepted. Add a corresponding read grant only where an endpoint actually requires it. Prove method-by-method permissions in the first hosted qualification, including registry credentials and delete, and show missing grants without requesting a Global API Key or silently broadening privileges. Optional usage imports can use a separate read-only analytics credential if required. Account billing edits, token administration, Access policy write and unrelated product grants are excluded from the standard token. Account-level Workers and Containers grants may reach unrelated resources. Use a dedicated account where possible and independently verify ownership before every mutation. ## Scaling, Placement and Spend

Build on `worker_pool/controller.py`, `external_controller.py`, `eligibility.py` and `claims.py`. The API owns the queue signal and reservations. The provider's `capacity-core.mjs` state machine, ScopeRegistry and per-incarnation ledger enforce independent ceilings and confirm physical exit. Use a persisted desired policy in place of hand-edited Cloudflare scope settings.

- Pack current compatible workers and prepared/starting reservations first. Measure eligible queue depth and oldest eligible wait, active claims and declared slot or memory fit. A single short queue fluctuation should not cold-start an instance. Use existing wake hints and periodic sweeps with a configurable sustained queue target and cooldown. A healthy, reconciled VM primary gets the first capacity action and owns the Normal warm floor. Preserve separately reserved Fast Path capacity.
- When the VM reaches its live ceiling and compatible unmet work remains, start Workers launchers for approved Normal work. Prefer ready compatible Workers slots to a new launch. Containers take qualified Linux-only overflow when the VM cannot fit it. Keep planning and claim predicates aligned. The VM can still win a compatible claim if a slot opens. Any later deterministic handoff must use the existing fenced queue reservation and bounded handback.
- Every reservation transaction applies the shared managed-worker limit, per-scope instance limit, per-launcher slots, aggregate Workers slots, compatible memory, tenant exclusion and budget. Count starting and uncertain releases, across current and retiring generations, until confirmed. Configure the provider registry and Container hard ceilings within that same envelope. A reconciled, healthy Workers scope remains usable when Containers discovery fails. A failed VM-primary reconcile blocks new overflow starts. Idle retirement requires continuous idle time and no admitted work, preserves the VM floor, and uses the existing drain/retire/release path. Keep Cloudflare warm floors at zero. Measure idle cost from outbound WebSockets, which can keep DOs active.
- Place the control-path DOs near the Bifrost API by initiating first contact from Bifrost and using an optional API-region location hint for new objects. Keep tenant-affine execution stable during a claim and avoid relocating active DOs. Test Worker Smart Placement or an explicit placement hint for the stateless provider/gateway only where measured origin round trips improve. Container placement can differ from DO placement and depends on image availability and available instances. Record API-to-launcher RTT, time to ready, queue-to-entry, SDK RTT, and bytes by direction. Keeping the hot API nearby reduces repeated hops and possible origin or cross-region transfer charges. A hard residency requirement needs an independently qualified jurisdiction constraint for every runtime and store, or that work stays local. [Workers placement](https://developers.cloudflare.com/workers/configuration/placement/) · [DO data location](https://developers.cloudflare.com/durable-objects/reference/data-location/) · [Containers placement](https://developers.cloudflare.com/containers/concepts/architecture/)
- Reserve monetary headroom transactionally with admission. Use a versioned conservative rate table and upper bounds on pending starts, launcher/DO lifetime, execution CPU, subrequests, storage/log volume and Container instance time, memory, disk and applicable network usage. Enforce transfer and log allowances at the gateway and in the runtime. Keep work that requires unbounded direct Container egress on the VM. Reserve an explicit drain/cleanup margin and a finite lease. Preserve exposure across transport failure, process restart or month rollover. Refuse new Cloudflare work when pricing or accounting inputs cannot bound it, telemetry is stale beyond the declared tolerance, or observed plus outstanding reserved cost would cross the operator limit. Let active work settle within its paid envelope and scale down. Reconcile estimated usage against provider readback and label invoiced charges separately. Treat the limit as a Bifrost admission guard, since provider metering can lag and fixed fees or residual provider usage may continue. [Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/) · [Containers pricing](https://developers.cloudflare.com/containers/platform/pricing/)
- Read back provider spend controls if authorized. Cloudflare offers account-wide Workers and DO blocking limits and budget alerts. Blocking limits can also interrupt remote recovery and cleanup calls. Phase 7 used an account notification to report spend. Bifrost does not change account-wide limits by default. Qualify local admission and expiry even without an alert, and show explicit consequences of provider-level suspension. [Cloudflare spending limits and alerts](https://developers.cloudflare.com/billing/manage/spend-management/)

## Lifecycle and Recovery

Use `capacity.cloudflare_enable`, `capacity.cloudflare_upgrade`, `capacity.cloudflare_reconcile` and `capacity.cloudflare_disable` PlatformJobs, registered with versioned payloads, explicit retry/timeout/memory policy, progress and terminal outcomes on the shared transports. Keep all four on trusted Bifrost infrastructure. Disable handles both Scale In and Disconnect. The existing fenced scheduler enqueues reconcile after a desired revision or health change and on a bounded sweep. Use shared PlatformJob waiting/resume for long drains and backoff where applicable. Cancel before external effects if allowed. Once effects begin, reach a durable safe checkpoint or reconcile to the current desired state.

Persist a platform-global connection and policy revision, immutable deployment generation, exact inventory and credential references. Put provider intent and readback receipts on owned resource records before and after network calls. These records represent infrastructure state. PlatformJob owns attempt, lease, progress and terminal state. Serialize incompatible changes by installation and desired revision in addition to per-operation job deduplication. Pass only IDs and expected revision in job payloads. Revalidate Global permission on user requests. Use the [repository authorization model](../../../../api/src/repositories/README.md) for workload scope. Provider account membership grants no organization reach.

- **Drift and partial failure.** Compute expected configuration from the signed release and policy revision. Compare names, IDs, bindings, artifact digests, tunnel rules and caps. Persist a deterministic intended name/identity before creating a resource. After timeout or runner loss, inspect exact account, namespace association and owned identity before deciding whether to adopt, resume or delete. Use paginated independent inventory checks, including after ambiguous deletes. Never adopt by prefix alone or overwrite a conflicting unowned object. Honor retry-after and distinguish a verified absence from authorization failure. Maintain one fenced desired state and prevent late creates after teardown begins. Unknown effects keep budget and capacity reservations held. A successor observes any in-flight external mutation through the provider's documented completion semantics before clearing that resource. Where those semantics cannot bound a late create, keep sweeping its intent and leave cleanup open. Retry recoverable failures. Ownership conflicts stop and surface the exact record.
- **Matched upgrade.** Stage a new named generation with matched Worker bundles, Container image, control protocol and policy. Keep the prior cloud generation accepting only its existing claims after switching admission. The new API must still serve draining protocols and callbacks. Release CI checks the compatibility window. Once the new generation passes a no-effect signed canary, admit new work and allow old claims, inventories and terminal ACKs to settle. Use spare headroom within the existing cap for canaries and overlap. With no headroom, drain old cloud capacity to make room and let compatible VM capacity serve meanwhile. If versions cannot overlap safely, drain before rolling the Bifrost API. Retain old resources and image while rollback is supported. Rollback reopens a still-compatible, fully verified generation under the same cap. A spontaneous DO reset uses the existing reconnect, inventory and terminal replay path. The recorded in-flight reset settled as `LauncherReset` / `uncertain`. Never dispatch such a route again merely because its transport disappeared.
- **Scale In and Disconnect.** Close admission and new starts under the same pool fence. Settle active claims and collect ACKs, or apply the existing bounded lease-loss and cancellation policy. Observe and release each launcher and require independently verified physical Container stop. For Disconnect, remove public provider entry points and bindings in dependency order, then remove owned applications, scripts and DO namespaces, and registry tags once nothing references them. Remove the DNS record, stop the supervised connectors and remove the tunnel, verify absence or a provider deletion tombstone with zero connectors. Preserve worker-control ingress until drain ends. Read back zero owned active resources for every resource class, then purge local credentials. A Worker delete alone does not remove its Container app. [Containers application and instance operations](https://developers.cloudflare.com/api/resources/containers/)
- **Revoked or narrowed token.** Treat a provider authorization failure as **Reconnect Required** after checking the credential and account, separately from timeout or rate limiting. Close admission and stop new provisioning or runtime lease renewals except a bounded authorized drain. Continue known retirement with the existing signed runtime channel while it works. For provider-side teardown that requires the revoked authorization, leave the audited inventory and remaining exposure visible as **Cleanup Pending**. Expiring runtime leases and provider time limits bound active compute. Removal of provider objects still requires a valid replacement token for that account. Resume at readback using the replacement, with no assumption that the last mutation failed.
- **Deleted Worker or tunnel down.** Mark the affected scope degraded and close admission. Keep the VM and independently healthy scopes available. For a deleted Worker, fence the lost generation, settle ambiguous attempts with existing loss semantics and account for its surviving Container app or namespace before recreating. For a tunnel outage, retain reservations and allow bounded reconnect and terminal replay with the same identity. Check connector state, exact DNS and ingress, then repair in place when the ownership proof matches. On lease expiry, fence the lost launchers, settle uncertain work and reconcile deletion. A rebuilt scope must pass signed readiness again.

## Implementation Plan

Each phase is an independently releasable increment with blocked work kept behind capability gates. Estimates are engineer-weeks including focused verification, excluding waiting for hosted authorization, provider support or account entitlement. Match hosted evidence to the exact release artifacts and runtime configuration. Use disposable accounts/resources, fixed caps, a time and cost envelope, negative-route probes, and verified teardown for every hosted phase. All model fixtures use a deterministic local or private HTTP stub. Deny real provider egress and use no live LLM credential, with call-count and usage assertions against the stub.

Proposed resource API is `GET/PATCH /api/capacity/cloudflare` for redacted desired/observed configuration, with write-only connect and rotate inputs and POST actions `enable`, `scale-in`, `disconnect`, `upgrade` and `reconcile` on that resource. Lifecycle actions return `202 PlatformJobAccepted` and the shared Location. Map every action and field to `bifrost capacity cloudflare` and thin HTTP-bridge MCP tools. Supply tokens through the existing protected secret-input path, with no token in CLI arguments, tool transcripts or responses. If MCP lacks a protected secret input, use an opaque credential reference for every surface until a supported secure input is available. Browser job progress uses `platform_job_updated` on the existing notifications WebSocket. CLI wait uses the shared PlatformJob endpoint. No feature-specific job status endpoint or browser polling.

Define shared Pydantic DTOs and authorization, run `./test.sh tests/unit/test_dto_flags.py` and `./test.sh tests/unit/test_contract_version.py` for each contract-changing phase, and regenerate skill truth and TypeScript OpenAPI types through the documented paths. Update the fingerprint and minimum CLI version according to the compatibility rules. Platform credentials and provider resource state stay out of portable manifests. Each job needs visibility, deduplication, versioned payload, runner lease-loss and structured-failure coverage. ## Risks and Open Questions

The hosted reset proved durable terminal replay, with an uncertain interrupted attempt. A drain-first upgrade and its rollback need their own release gate. Registry cleanup and the exact Containers permission/application sequence need qualification from the packaged Bifrost runner. Unknown physical capacity, stale cost measurements and provider-wide spend suspension can delay placement or cleanup. Keep those states visible and fail closed on new cloud work. Region selection remains best-effort unless a supported jurisdiction policy is independently qualified.

1. Should the first production release require a dedicated Cloudflare account, or allow a shared account with account-scoped Workers and Containers permissions?
2. Should one-button Managed Tunnel launch on the packaged single-host install alone, or also on existing Kubernetes and other multi-replica installs?
3. Should approved workloads use unrestricted Cloudflare placement by default, or must the first release enforce a specific data jurisdiction?
