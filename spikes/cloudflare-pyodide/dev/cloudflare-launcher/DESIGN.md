# Cloudflare launcher: Workers as an external worker in the upstream pool

Status: phases 5a and 5b passed on the fork, 2026-11-18. Targets upstream
`main` (Jack's merged
capacity core, #1423) and stays compatible with the direction of #1424
(API-owned compute, derived worker keys) and #1425 (Cloudflare Containers
provider). Workers for Platforms is out of scope.

## Why this shape

On upstream `main` the API already owns the whole execution lifecycle for
remote capacity:

- `api/src/worker/remote/host.py` runs the worker loop **inside the API**:
  claims (`worker_pool/claims.py`), admission by memory, fencing
  (`remote/fencing.py`), canonical result commits, credential issue and
  refresh.
- The remote side is a thin **launcher** (`remote/launcher.py`): it dials the
  API over a WebSocket, sends a signed `hello`, executes `command` envelopes
  (`workflow`, `agent_run`, `platform_job`, `terminate`, ...), and emits
  `event`s (`result`, `sample`, `inventory`, `draining`). Terminal events are
  retained until the API sends an `ack`.
- Capacity providers (#1423 `capacity_core.py`; #1425 Cloudflare Containers)
  only create and observe launchers (`prepare`/`start`/`observe`/`release`).
  They are never a job transport.

So the compatible way to put Cloudflare Workers into that pool is **a launcher
that runs on Cloudflare**, not a second dispatcher. Everything the spike
already proved (per-tenant engine child, TenantApi outbound gateway, warm
host, attempt deadline, compiled runtime) sits *behind* that launcher. The
existing spike pieces that duplicate API ownership (`backend/private_http_pool.py`
relaying from inside the API) are not carried forward.

## Pieces

### 1. Launcher Durable Object (Cloudflare side, new)

One `CloudflareLauncher` DO per launcher incarnation (`launcher_id`,
`incarnation_id`, `resource_uid`). It:

1. Opens an **outbound WebSocket** to the API's remote-control endpoint
   (`connect_control` equivalent), and keeps it while it holds work or is
   inside its idle window. A DO holding an outbound socket stays resident;
   that is the cost of being a launcher (≈ one 128 MB DO, billed by
   duration, only while the capacity controller keeps the launcher started).
2. Sends `hello` signed with a **derived worker key** (below), advertising:
   - `form: "external"`, `resource_uid`, lane `normal`;
   - `runtime_profile: "cloudflare-python-v1"` inside the signed bytes;
   - `handlers: [["workflow.execute", 1]]` only. No agent, summary,
     platform-job or package-tool handlers;
   - `credential_protocol: 2` (run access token + refresh challenge).
3. Handles commands:
   - `workflow` → validate, then hand `(execution_id, context)` to the
     tenant's `TenantHost` (`run()`), keyed by the context's organization.
     Reply with a route acknowledgement (no PID; see API side).
   - `terminate` → retire that tenant child's generation (best effort; the
     platform offers no physical kill) and emit a terminal for the route.
   - `ready` → mark the launcher ready.
   - anything else → error reply (not advertised, so the API never sends it).
4. Emits `result` events with the engine's result, keeps them in DO storage
   until `ack {event_id}`, and replays unacknowledged terminals after a
   reconnect, exactly like `launcher.py`'s `pending_terminal_inventory`.
5. Answers `inventory` with its live routes (route id, execution id, started
   at, timeout, memory request) and retained terminals.
6. Emits a `heartbeat` once per second with liveness and slot occupancy.

The protocol core (canonical hello bytes, HMAC proof, envelope
encode/parse, fragmentation and reassembly, sequence and generation fencing,
terminal retention) is a pure module, tested against vectors generated by
the Python `protocol.py`, so the two implementations cannot drift silently.

### 2. Authentication: derived worker keys, never the platform secret

Legacy Linux control hellos still use the platform `secret_key` until
#1424's coordinated cutover. #1424 adds
`shared/worker_control_auth.py::external_worker_control_key(provider_key,
worker_id, resource_uid)`: an HMAC of the incarnation and resource under the
provider's capacity credential. The Cloudflare launcher holds only that
derived key (a Worker secret, per incarnation), and the API derives the same
key to verify a Cloudflare `external` hello. We adopt #1424's function byte-for-byte
(same domain string, same JSON binding), so it merges cleanly when #1424
lands.

### 3. API side (fork, minimal, behind a setting)

- Admit `runtime_profile == "cloudflare-python-v1"` only for the external
  Normal lane when `BIFROST_CLOUDFLARE_WORKER_HELLO_ENABLED=true`.
  This operator environment or `.env` setting defaults to false.
- For that profile, require the advertised handlers to be exactly
  `workflow.execute@1`, and treat the route acknowledgement without a PID as
  valid. No fake PIDs.
- Resource accounting by **declared request**. The API assigns each launcher
  one to four slots from its prepared capacity reservation. Each claim holds
  one slot and its request (up to 128 MiB) until settlement.
- **Eligibility at claim time.** A Cloudflare launcher must only claim
  executions the Pyodide runtime can run (no unpackaged native dependencies,
  within subrequest/CPU limits). The fenced claim uses the API's durable
  approval marker for the Normal workflow handler. The first version only
  approves explicit, reviewed workspace fixture revisions.
- Termination: the API's deadline and cancellation paths already end in
  `terminate`; for this profile the terminal is reported as a cooperative
  stop, and the existing fencing keeps late effects from committing.

### 4. Capacity and bursts

- Scale-out stays with the API controller (`launch_for_demand`): more queued
  work → more launcher incarnations, up to `max_workers`, through a provider.
- A Workers provider for #1423's `capacity_core` is small: `prepare` writes
  the incarnation's derived key and identity into a DO, `start` tells the DO
  to dial in, `observe` reads its state, `release` tells it to drain and stop.
  #1425's `ScopeRegistry`/`WorkerLedger` DOs are the model.
- **Burst on VM overload** is then the controller's normal behaviour: when
  the VM's workers are full, demand launches Cloudflare incarnations.
- Pack different tenants onto one launcher to reduce the number of resident
  control sockets. Each tenant still has one TenantHost and engine child. Fork
  issue #54 proposes overflow children for same-tenant bursts. This change
  leaves that child lifecycle for separate work.

## Review (GPT-6.2 Sol, 2026-11-18): request changes before enabling claims

Verdict: the shape is right, but three blockers must be designed before
Cloudflare may claim work: cancellation after a child starts, recovery after
launcher eviction, and planning that could reserve work the launcher cannot
run. Findings, checked against the cited code:

1. **Launcher protocol details the summary missed.**
   - Send `inventory` right after `welcome`, before reading commands, then
     replay retained terminals.
   - Replies are `event` envelopes, `{reply, result}` or
     `{reply, error_type, error}`.
   - Persist the next `hello_sequence` before dialing, including when the
     welcome is lost.
   - Reject stale generations and sequences in both directions.
   - Agree a logical size bound for reassembly (Python spills to disk).
   - Persist `event_id`, terminal and adoption metadata together; delete on
     the fenced `ack`; keep receiving acks while draining.
   - The external build version must match the prepared row.
2. **PID-less routes.**
   - Adoption already tolerates a missing PID. Workflow and service *spawn
     replies* require a positive one, and a missing PID takes the
     hard-error path even if execution started. PID-less routes also drop
     out of heartbeat counts.
   - Cloudflare inventory must be v1 with live *and* terminal route
     metadata. The `baseline_bytes` field is required for Linux inventory.
3. **Samples and admission.**
   - The hello sample is mandatory.
   - Missing periodic samples close admission after 3 s and eventually
     expire ownership.
   - Admission holds `max(request, growth)` against
     `limit × threshold − baseline`. So "slots × request" as the limit loses
     capacity to the threshold and cannot enforce a slot count.
   - Needed instead: explicit slot and byte reservations, independent
     liveness, telemetry labelled as declared, and declared usage kept out of
     Linux calibration and learned peaks.
4. **Termination.**
   - The API terminates by route; the Linux launcher enforces timeouts,
     pressure shedding and TERM/KILL.
   - `TenantHost` races its deadline only *after* queueing, and can leave
     the old child running.
   - Third-party egress is checked against whichever attempt is current.
   - Required: attempt-bound egress revocation, a deadline covering queue
     time, and explicit handling of uncertain execution. API fencing
     protects commits, but already-issued external requests can complete.
5. **Credentials.**
   - Use #1424's key derivation together with its enrollment: the capacity
     token goes to the API and the provider, only the derived key goes to
     the incarnation, revocation retires the row and closes the session, and
     token rotation is coordinated.
   - Credential protocol 2 issues **two** run tokens (access and refresh).
     The gateway hides only `engine_token`; both must stay behind it.
6. **Eligibility in the fenced SQL claim, not after it.**
   - Persist an API-computed, revision-bound eligibility marker at enqueue.
   - Apply the same predicate to candidate selection and head-of-line
     blocking, including reserved dispatches.
   - Carry it into planner packing, reservations and idle decisions.
   - Main selects a single managed provider, so VM-then-Cloudflare burst
     placement needs an explicit policy.
7. **The Durable Object is viable with bounded recovery.**
   - Outbound sockets cannot hibernate; they protect against eviction for
     up to 15 minutes per connection, billed at 128 MB resident.
   - Needed: alarm-driven reconnect, durable route state, and uncertain
     routes fenced against redispatch.
   - A Container relay is the fallback that keeps the outbound protocol.
8. **Capability gates first.**
   - #1424 sends `bootstrap` after every welcome and plans from
     build-matched capabilities.
   - Main calls `package_tool` during startup and starts service and
     platform-job loops regardless of advertised handlers.
   - Those gates and the PID-less contract must be defined before any
     launcher talks to a real host.

## Phases (revised after review)

1. ~~Protocol core in JS + Python-generated conformance vectors.~~ Done
   (`protocol.mjs`, `vectors.py`, `conformance.test.mjs`).
2. ~~**Execution-side safety the launcher depends on**, in the spike's own code.~~
   Done after three review rounds (commits `536d59ace`, `bfbaec816`,
   `aa8d5e849` and the follow-up):
   - **Both protocol-2 run tokens stay behind the gateway.** The gateway
     never replays a request. It forwards once and records the API's
     `refresh_required` challenge. It answers the SDK's own `/auth/refresh`
     with the handle, after refreshing the real tokens single-flight and
     only once a challenge was seen. A temporary refresh failure answers 503
     and keeps the refresh token.
   - **The deadline runs from the supervisor's dispatch.** That covers queue
     time and the warm-up retry. Queue waits stop at the deadline. The
     deadline is rechecked after the durable in-flight marker, immediately
     before the child dispatch.
   - **Sends start inside the host.** SDK calls and egress begin in the same
     synchronous turn as the liveness and permission check. Bookkeeping
     writes are `allowUnconfirmed`, so nothing holds a send at the output
     gate past its check.
   - **Generations are fenced.** A host reset mid-attempt retires that
     generation via the marker. Readiness follows the generation that
     answered.
   - **Every engine outcome names its `attempt_state`.**

   Cloud lab (self-origin, 1.5 s deadline): each call sent exactly once;
   queued attempts past the deadline came back `not_started` with zero
   calls; one mid-run expiry came back `uncertain`; the next attempt
   recovered on a fresh child.

   **Accepted residuals**, all within one tenant's trust boundary:
   - A request already started may finish after its attempt ends.
   - Third-party egress carries no attempt identity. A background request
     left over from attempt A that reaches the host during attempt B, in the
     same child, is judged by B's allowlist and logged against B.
   - A one-shot streamed upload cannot be replayed after a refresh challenge.
   - Large uploads are now bounded by the Durable Object's outbound body
     limit (100 MiB).

### Phase 6 managed capacity

- The authenticated capabilities response declares the scope's
  `runtime_profile`. Existing v1 providers that omit it launch
  `linux-process-v1`. Changing a scope's profile requires draining it and
  enrolling a new scope. Reserve Cloudflare rows with `cloudflare-python-v1`,
  `workflow.execute`, and the incarnation UUID as the pre-bound launcher ID.
  Commit the provider UID and `starting` state before calling start. Hello
  verifies this binding and opens admission after inventory reconciliation.
- One external scope still works on its own. Dual mode explicitly configures
  a primary Linux scope and a distinct Cloudflare burst scope with separate
  tokens. Pack existing capacity as in phase 3, including declared slots for
  pending Cloudflare starts. Give Linux the first chance to launch. When its
  scope reaches its advertised worker ceiling, Cloudflare can start for
  remaining approved Normal workflows that fit one 128 MiB declared slot.
  Linux reconciles independently of burst discovery. Burst launches require
  a successful primary reconciliation and count only live Linux
  incarnations toward the primary ceiling. Unconfirmed terminal resources
  still consume physical capacity until cleanup. Static Linux workers
  participate in packing when Cloudflare is the sole managed scope.
- Both scopes use the existing reservation lock and shared managed-worker cap.
  Only Linux workers count toward the Normal warm floor in dual mode.
  A sole Cloudflare scope can maintain the Normal warm floor. Cloudflare
  never supplies Fast Path or Linux memory probes. Idle drain and rotation
  use the existing lane floors and profile-specific fit. Only a Linux
  controller with room in its own scope and unmet Linux demand or a Normal
  warm floor deficit may make an idle Cloudflare worker yield a shared slot. The worker's owning scope
  reconciles physical deletion.
- The Workers provider holds the dedicated capacity token in its own Worker
  environment. Its `WorkerLedger` derives the key using the incarnation and
  resource UID, and sends only the identity and derived key to the launcher
  DO over a private binding. Prepare persists that enrollment without dialing.
  Start records durable intent and schedules the first dial. Observe reads
  the reservation, accepted start and socket state. A failed enrollment
  frees its scope slot and retains its UID. Prepare or start can retry that
  enrollment. The API bounds both phases by the incarnation's start
  deadline. Only authenticated API hello grants work.
- The API drains and settles work while its row is live. It sends release
  only after retirement or loss, when ownership is fenced and terminals
  can no longer be delivered. Release immediately stops the socket and
  alarm, revokes the enrollment key and fences late results. An active
  route gets a best-effort cooperative stop. External requests already sent
  may still finish. The provider confirms launcher stop, frees the scope
  slot and records deletion before reporting success.
- As in #1425, `ScopeRegistry` serializes the scope ceiling and `WorkerLedger`
  serializes operations for one incarnation. An uncertain start is observed
  before retry and can be retried only on durable proof it never reached the
  launcher. An accepted start can reconnect on its own alarm. Failed reads
  and unconfirmed stops retain the record and its slot. A tombstone prevents
  resurrection after retry or reset.

### Phase 6 extension: Cloudflare Containers for Linux overflow

Design and compatibility findings at fork base `87d9daab1`, compared with
`origin/pr-1425` at `bdbe07f93`. The first implementation covers Linux
workflow overflow. Platform-job parity still requires the workload
contract described below.

**Placement.** Add an opt-in third managed scope alongside the VM primary
and the Workers burst scope. The Containers provider launches a Normal
`linux-process-v1` process. Scope identifies the capacity provider and
runtime profile identifies the execution protocol. A third scope keeps the
VM available for the warm floor and work that still needs its trusted data
plane or isolation, while allowing both Cloudflare runtimes to burst.
Replacing the VM primary would remove that capacity before parity is
established.

- The VM remains the primary and supplies the Normal warm floor. Existing
  Linux and Kubernetes behavior stays on its current path when the third
  scope is disabled. Existing Fast Path and isolated-build placement remain
  on their explicitly configured infrastructure.
- When the VM reaches its advertised live-worker ceiling and work remains
  uncovered, prefer Workers for revision-approved Normal workflows
  (including approved install-local Solution workflows) and qualified
  summaries. Agent runs stay on Linux until their Workers handler passes
  qualification. Use the existing approval, handler, slot and tenant
  predicates in both planning and fenced claims. For a deterministic
  overflow handoff, the API must fence the selected dispatch to the Workers
  reservation with a bounded handback through the existing queue. Planner
  preference alone cannot prevent a newly free Linux worker winning the claim.
- Containers supply remaining Linux-only demand that their build and
  authenticated runtime contract can handle. Initial targets are native
  workflow execution and live package tools. Git, app/Solution compilation,
  service children and long platform jobs each need their own qualified
  data and lifecycle contract. Privileged jobs lacking such a contract
  stay on their current trusted backend. Build-class jobs retain their
  isolation requirement even when the image can run npm and Vite.

**Capacity.** Use the existing API reservation lock and one managed
`max_workers` across the three scopes, plus each provider's own physical
ceiling. Count live reservations and unconfirmed terminal resources against
physical headroom until the owning provider confirms cleanup. A shared cap
equal to the VM ceiling leaves zero overflow slots. Keep the Normal warm
floor within the VM scope ceiling and both Cloudflare scopes demand-only.
Preserve existing Fast Path reservations. A failed peer discovery or failed
primary reconcile cannot authorize new overflow starts. Independently
reconcile known resources and allow owned cleanup during a peer outage.
Validate scope identity, memory, lifetime and aggregate capacity on policy
save and admission. Keep Linux measurements keyed by scope and build.

**Adopt from #1425.** Keep the v1 capacity HTTP shapes, the ScopeRegistry,
WorkerLedger and WorkerContainer lifecycle, the prepare/start split, UID
checks, ambiguous-start observation, terminal tombstones and inactivity hold.
Use the provider's derived-key environment contract
(`BIFROST_WORKER_CONTROL_SECRET`) and the existing, identical #1424
`external_worker_control_key` function. The capability response may continue
to omit the profile because the fork already defaults it to
`linux-process-v1`. Keep the upstream provider unit suite and use the shared
black-box conformance suite. Use a local physical-launch hook for Docker
qualification and reserve the upstream dashboard hook for an authorized
hosted run.

**Fork adaptations.** #1425 selects one external provider and assumes
#1424's API-only launcher and build-matched capability negotiation. Extend the
fork's existing primary/burst policy with a separately configured URL/token
pair and distinct scope. Extend the existing controller's count and placement
logic so the two Linux scopes remain distinct and all three share one cap.
The API must select the Containers token using the canonical reservation's
scope and verify a signed Linux hello against its incarnation UUID and
resource UID, including reconnects. A Containers reservation must accept
only the derived proof. Preserve legacy Linux authentication for deployments
without this scope. The provider and API keep the scope's capacity token.
The container receives only its derived control key and separately scoped
work credentials. Installation signing/encryption, database, Redis and
storage credentials stay with the trusted platform. Drain and confirm
resource deletion before scope or token replacement.

**Image and runtime.** Pin the fork's Linux worker image by digest, with a
build version that matches the reserved and reported version. Use #1425's
launcher entrypoint and normal-lane identity. The image needs the locked
Python runtime, dependencies and native system libraries, Node/npm and Vite
build tooling, Git and CA certificates, a writable disposable package
environment, and enough writable disk for image layers, source trees,
build output and pip/npm caches. Supply compilers and headers where a
qualified package needs source builds. Pass requirements through authenticated
bootstrap. Broker Git inputs and private registry access at job scope and
keep job leases, publication and durable results under the API's authority.
Measure cgroup budget, image startup, build CPU and disk, package generation
recycle, service drain/reconnect and long-job handoff before advertising
each workload.

**Compatibility blocker.** At the fork base, `remote/launcher.py` reads
`BIFROST_SECRET_KEY` before hello, and `remote/host.py` verifies Linux
hellos with that key. The fork's launcher then invokes the existing
requirements helper, which reads the platform requirements cache directly.
The generic `platform_job` command starts `src.jobs.platform.runner`,
whose entrypoint initializes PostgreSQL and whose runner decrypts protected
payloads with platform authority. `solution.update_check` queries the database
and resolves repository credentials. `workspace.reimport` opens a database
session and materializes the workspace from platform storage. A derived
control key solves hello authentication only. #1425's environment rejects
these platform credentials. Its API-only host limits the generic external
job claim to supported compute stages, and its catalog places
`solution.update_check` on the API. Its staged App compiler illustrates
the split but supplies neither a Container runner for the requested jobs
nor isolated-build parity.

### Phase 3 workspace approval and placement

A server operator runs these commands inside the API container, from `/app`:

```sh
python -m scripts.cloudflare_workflow_approval propose WORKFLOW_UUID --subrequest-allowance 10 --cpu-budget-ms 1000 --https-host '*.halopsa.com'
python -m scripts.cloudflare_workflow_approval accept WORKFLOW_UUID --subrequest-allowance 10 --cpu-budget-ms 1000 --https-host '*.halopsa.com' --review-sha256 REVIEW_SHA256 --operator OPERATOR_LABEL
python -m scripts.cloudflare_workflow_approval revoke WORKFLOW_UUID
```

Review the complete proposal and the pinned source against the expected inputs,
dependencies, HTTPS destinations, and resource usage. The digest covers the policy
version, workflow and owning organization, prior approval, entry and module
SHA-256 pins, canonical manifest digest, packages, HTTPS allowlist, and both
estimates and limits. Accept regenerates the proposal and checks the reviewed
digest. PostgreSQL stores the accepted revision and operator label. The command
requires trusted server access and has no HTTP or tenant-facing surface.
Revocation clears the current approval and makes later runs Linux-only.
Earlier approvals and derived children remain inactive in history with their
lineage intact. A queued reanalysis becomes superseded and a queued dispatch
fails send-time approval verification. A new human acceptance is required
after revocation. A run already past the final send-time approval recheck
is still sent.

The analyzer is a review aid. It is not a sandbox. TenantHost and the runtime
enforce the security boundary. The offline census uses the same AST analyzer
and pinned Pyodide 314.0.6 stdlib list as the server. The list is the union of
top-level modules in the Workerd runtime's `python314.zip` and
`sys.builtin_module_names`. A loopback probe of the pinned bundle successfully
imported `ssl`, `sqlite3` and `lzma` without loading extra packages. It resolves
transitive workspace imports, rejects known Pyodide traps, and discovers literal
HTTPS origins. The analyzer follows imported HTTP namespaces, known clients, and supported
fetch functions. It proposes exact hosts from HTTP call URLs and client base
URLs, and reports `unresolved_url_calls` when static analysis cannot establish
a destination. Returned links, documentation strings, and schema identifiers
do not become egress permissions. For per-tenant hosts or server-provided URLs,
an operator can repeat `--https-host` at proposal and acceptance with exact
destinations or a quoted `*.` pattern. The review output lists wildcard entries
first and the digest binds them as part of `https_hosts`. The analyzer only
proposes exact hosts and reports templated destinations as unresolved.

`*.halopsa.com` allows `acme.halopsa.com`. The base and deeper hosts such as
`a.b.halopsa.com` require separate entries. Use DNS hostnames in ASCII (IDN
A-labels), without trailing dots or ports. TenantHost accepts HTTPS on the
default port and counts matching fetches against the attempt's subrequest
allowance. A wildcard trusts every tenant subdomain of that vendor, so compromise
of another tenant's subdomain at that vendor is in scope. Exact entries can
limit this exposure.

A wildcard base must be under a recognized ICANN suffix and contain a
registrable domain. Shared-hosting zones are excluded using the registrable
roots of all private PSL rules, including their descendants. This also excludes
provider roots such as `amazonaws.com` that list shared zones at deeper labels.
The API and Worker ship generated data from PSL `2026-11-17_16-14-34_UTC`
(`09c1b150f33c6145a73afcf7db0fb872fc54b4d1`). To refresh, download the
[official PSL](https://publicsuffix.org/list/public_suffix_list.dat), then run
`node spikes/cloudflare-pyodide/dev/executor/generate-egress-psl.mjs public_suffix_list.dat`
from the repo root, update this pin, and run the shared matcher vectors.

The analyzer recognizes immediate `getattr` calls in private helpers defined
in the entry module when every reference is a direct call and supplies a
public literal selector. It counts the operation as an unresolved URL call,
without granting any host. Imported modules and unproven selectors retain
the existing refusal.
Before parsing, analysis limits raw source buffers
to 128 KiB per file and 512 KiB per bundle, with a single module AST processed
at a time and at most 100,000 visited nodes across the bundle. Python object
overhead is additional and the worker admission and memory limits apply.
The estimates are static sizing signals. A call site may execute
many times and CPU varies with inputs. TenantHost and the platform apply the
actual limits. Inline code, Fast Path and artifact-workspace dispatches are
outside this policy. Enqueue compares indexed digests and workflow identity
against the current approval without reading or parsing source.

For Solutions, the same operator command reviews the active workflow in its
install. The review records the install ID, declared version, published
runtime source generation and owner organization. A deploy clears the
generation in its first commit and publishes a new generation with the source
index after storage finalization. Existing installs need a successful
redeploy to acquire the marker. Only installs with outbound access disabled
are eligible. Imports must resolve in the install or the supported runtime.
Vendored modules count as install source. Approval never grants access to
shared workspace imports. Carry-forward analyzes the new generation under the
same install and owner, even when all source pins are unchanged.
Holders of `solutions.deploy` and git auto-pull can publish code that carries
forward automatically within the operator's approved limits. The same deploy
authority already allows that code to run on Linux with broader egress.

The first Normal dispatch to observe changed entry or module pins stays
Linux-only and queues a deduplicated `workflow.cloudflare_reapproval` PlatformJob.
The job loads the transitive sources outside the enqueue transaction. It may
replace the current approval when packages match exactly, each discovered host
matches an existing allowlist entry, and both estimates fit the current limits.
It retains the parent's limits and HTTPS allowlist, including any reviewed
wildcards. It records the parent approval and each added, changed, or removed
pin. The job fences
publication on its lease, the current approval, the workflow owner, and indexed
source digests. Later dispatches may use the derived approval. A deterministic refusal keeps that observation Linux-only until an analysed
path, including a dependency discovered by this analysis, changes in the file
index or an operator accepts a new proposal. Storage failures and unresolved
dependencies can retry through PlatformJob and be staged again after cooldown
when they are present in the index. Missing unindexed imports require review.
After workflow commit a best-effort background task stages the job in a short
transaction. A process exit before staging leaves the triggering run Linux-only,
and a later dispatch can try again. The shared queue releases its dedupe
lock at the end of that transaction, and the triggering Linux run can proceed
if staging fails.

Before sending `workflow`, the API repeats verification against the current
approval and source. The command context carries `cloudflare_workspace`
with the approved `manifest`, the exact verified UTF-8 `sources` keyed by
path, `packages`, `https_hosts`, `subrequest_allowance`, and `cpu_budget_ms`.
Solution snapshots also bind the install ID and carry the approved entry
digest on the command context. The API rechecks the install generation and
indexed pins after fetching the bytes. The run retains its ordinary
execution-scoped SDK credential and Solution context.
The launcher's install ID and entry digest comparison checks wire
consistency. The API verifies the source bytes before sending.
The launcher must execute that snapshot and enforce the declared outbound
policy. Missing, revoked or changed pins prevent a send and hand the run
back as Linux-only. Other definitive refusals retain the revision and
original queue age.

Linux remains eligible for every dispatch it can already claim. Planning
places eligible work on reconciled Cloudflare slots first, preserving
Linux capacity for requests only Linux can run. Actual claims retain
per-worker priority and queue order, with the first eligible claimant
winning. Linux retains its existing reserved-work priority and physical
memory gate. Managed launchers of either runtime count toward the shared
worker cap. Dual mode reserves the Normal warm floor for Linux across
placement, idle drain and rollout. The owning controller can rotate an
outdated Cloudflare launcher.
Calibration and measured Linux budget ceilings use Linux reports.
An idle, reconciled dev launcher with no eligible fitting demand can
yield a capped slot to a controller outside its scope. A controller
keeps its own launcher out of this demand-driven replacement path while
the planner assumes new starts are Linux. A live authenticated launcher that
could hold marked work can defer early rejection by a smaller Linux ceiling
until the ordinary queue deadline.

### Phase 3 opaque workflow wire contract

- First admission promotes the prepared row to `ready` in the same database
  update that acquires ownership. Reconnect and takeover recheck the same
  bindings on `ready` or `draining` rows. Retiring the row immediately revokes
  enrollment and makes the current database fence fail for control and
  transaction checks. When another actor marks the row `lost` or `retired`,
  liveness-only heartbeats can still refresh the in-memory transport timestamp
  until the host detects the loss or its tracked lease expires. The next
  renewal normally starts within 10 seconds for a connected, heartbeating
  launcher and fails the database fence. If the database is slow or
  unavailable, heartbeat acceptance is bounded by the remaining tracked
  lease (20 seconds from acquisition or renewal start). The host closes the
  socket during session cleanup. This keeps a database read off every
  launcher heartbeat while database-gated actions remain fenced.
  A fresh, verified Cloudflare hello matching a `retired` or `lost` row
  receives close code 4001 (`incarnation ended`). That code permanently
  stops reconnect for that incarnation. Other closes keep alarm backoff.
  Re-enrollment requires a new incarnation and derived key. The capacity
  provider is future work.
- The Cloudflare hello advertises the signed runtime profile and capabilities
  above and omits `sample`. The API derives the slot count and request byte
  budget from the prepared incarnation (134217728 bytes per declared slot).
  Capacity does not come from launcher-supplied fields.
  The API does not send Linux memory-pressure configuration or
  `memory_kill_growth_bytes` for this profile.
- Send a `heartbeat` once per second inside a normal sequenced event
  envelope for the current session generation. Include `occupied_routes`
  (route IDs, including retained terminals) for multi-slot incarnations, or
  `slot_occupied` for single-slot incarnations, and `received_sequence`, the
  last API frame received in that generation (zero before any frames).
  The API writes a busy slot in the claim transaction and only reports it
  free after both its hold and physical occupancy clear. Hello and reconnect
  start the freshness window, while inventory reconciliation independently
  gates claims. A heartbeat older than three seconds pauses admission and
  blocks new workflow sends. An expired heartbeat prevents owner renewal
  at the owner lease window.
  `sample` is a Linux event and does not refresh Cloudflare liveness.
- API pool heartbeats publish `runtime_profile` and `declared_capacity`
  (`slots`, `held_slots`, `budget_bytes`, `reserved_bytes`). Each invocation
  reports `memory_request_bytes`. Held values come from API claim
  reservations, including pending dispatches, unresolved launches and
  retained results until settlement. The byte budget has no baseline,
  pressure threshold, or growth adjustment. Cloudflare heartbeats omit
  measured process CPU and memory fields, and result resource metrics are
  discarded before persistence and peak learning.
- The workflow command's `route_id` is `workflow:<execution UUID>:<route UUID>`.
  Its `started_at`, `timeout_seconds`, and absolute `workflow_deadline` come
  from the API at dispatch. The deadline is also in the execution context.
  Preserve those fields unchanged for inventory after reconnect. A zero
  timeout carries a null deadline. The launcher must use the same deadline
  through queueing, warm-up retries, and child dispatch. If it expires
  before entry, journal a timeout terminal with `attempt_state: "not_started"`.
- Reply to workflow dispatch with `{runtime_handle}`. The handle is an
  opaque 1–255 character token using letters, digits, `.`, `_`, `:`, and
  `-`. Use the same handle for the route's lifetime and omit `pid`. A lost
  or ambiguous reply leaves the route reserved.
  Once the launcher sends the reply, a transport disconnect leaves the
  route eligible to enter the engine under its original deadline. The
  next inventory includes the route or its retained terminal. A route
  needs both confirmed storage and a sent reply to enter the engine.
- An error reply to a `workflow` command is a definitive refusal
  (`not_started`). The launcher has never entered and must never enter
  the engine for that route. If engine entry may have occurred and the
  outcome is unknown, journal an `uncertain` terminal. An explicit
  `MemoryError` refusal lets the API hand the claim back for redispatch.
- Once the launcher sends an inventory omitting a workflow route from an
  earlier control generation, it must never enter the engine for that route
  or report it in a later reply, event, or inventory. The API may already
  have settled the omitted attempt as uncertain.
- After welcome, send one inventory per control generation under the
  `inventory` key of the `{"event":"inventory"}` payload. It must contain
  `version: 1` and both `routes` and `terminal_routes` arrays. Omit Linux's
  `baseline_bytes`. Each entry carries `kind: "workflow"`,
  `route_id`, `subject_id` (the execution UUID), `runtime_handle`,
  `active_execution`, `started_at`, `timeout_seconds`, `workflow_deadline`,
  and the original `memory_request_bytes` from the workflow command. The API
  restores one slot and these bytes for each matched route before reopening
  claims. Terminal entries also carry `event_id` and
  `attempt_state`. The API checks the snapshot against live durable claims
  and routes already tracked by that owner. A claim still preparing to
  dispatch can be absent from inventory. An omitted route whose launch was
  never acknowledged settles individually as uncertain, including an
  interrupted send. An unclaimed live route, an omitted acknowledged
  route, or another claim/route mismatch loses the worker and settles its
  outstanding runs under the ownership fence. A tracked invocation may
  already have run even when the current inventory omits it. Runs failed by
  inventory loss are never redispatched.
- A `terminate` command carries `route_id`, `error_type`, and `error` in the
  current control generation. `{received: true}` acknowledges the stop
  request only. The API bounds this request, retains the route if the reply
  is lost or ambiguous, and waits for terminal settlement. A replacement
  owner can issue a route stop for a still-live cancelled or expired claim,
  so the launcher must treat stop as idempotent by route.
- Journal `result` events with `route_id`, `runtime_handle`, `_event_id`,
  `attempt_state`, and the usual `result` object. Replay the same event
  after inventory with the same ID and attempt state. Use `not_started`
  if the engine was never entered, `completed` for an observed engine
  outcome (including a workflow error), or `uncertain` if side effects may
  have occurred without a confirmed engine outcome. Only `completed` may
  carry a success. The API settles a user stop as `Cancelled` and a deadline
  stop as `Timeout`. A classified Cloudflare CPU or memory kill stays
  `uncertain` and settles as `Failed` with `CpuLimitExceeded` (including
  `cpu_budget_ms` in the message) or `MemoryLimitExceeded` (platform limit).
  These terminals omit platform exception text and resource measurements.
  All `uncertain` terminals warn that effects may already have occurred.
  Other `uncertain` terminals fail with `WorkflowAttemptUncertain`. The API
  acknowledges terminal delivery under its owner fence. A stop reply alone
  never releases a reservation.
  When recovering an engine-entry marker after a launcher reset, the
  launcher also requests a best-effort TenantHost stop for that route.
  TenantHost wakes cancelled queued attempts and returns `not_started`
  while the predecessor continues to hold its place.
- The Cloudflare logical envelope limit is 16 MiB, with individual frames
  capped at 1 MiB. With one message assembling at a time, the limit leaves
  room within a 128 MiB isolate for fragment buffers, the joined bytes,
  decoded JSON, and source copies for dispatch. The API checks serialized
  size before its first send. An oversized workflow returns to the queue
  with its Cloudflare revision cleared. The launcher enforces the same
  bound during reassembly.

### Artifact-workspace follow-up

The nearest extension is an approved Normal workflow invoked as an agent
tool with an inherited artifact workspace. The agent executor selects the
root ancestor run ID (or its current run ID) and passes it in pending
execution context. The durable workflow authority identifies the originating
agent definition and users, but does not bind this execution to that agent
run or workspace. Current artifact APIs authorize row access using original
user reach and privileges. In particular, the write service can initialize
an empty workspace within that user's reach, so success there cannot prove
the workspace belongs to the invoking run.

Record a server-verified artifact workspace binding during workflow
acceptance. Derive it from the invoking agent run and its durable ancestry.
Validate that the agent run, execution owner and target organization agree
with the existing tool authorization. Store the binding on the execution
and load it through the workflow runtime credential. At dispatch, compare
the pending workspace against that binding in addition to the ordinary
source approval. Forward the workspace in the context and apply the same
binding to artifact SDK requests for this execution. Keep the existing
artifact row authorization as an independent check.

The launcher test exercises only the refusal for an artifact-workspace route.
It sends the same approved snapshot with and without an artifact workspace
ID. The request carrying the ID is refused before host entry. The control
enters normally. Workspace binding remains a design. Before enabling this path,
test a child tool writing and reading one artifact in its ancestor workspace,
a mismatched workspace in the dispatch and SDK request, and an empty
workspace owned by a different organization. Include raw bytes or multipart
input through the Worker gateway and confirm the run token is revoked at
settlement.

The provider call should run in trusted Worker code outside TenantHost. A provider
secret must be unavailable to workflow children, including through the
generic egress path. The provider adapter must use a fixed origin and path,
reject redirects, cap request and response bytes, and avoid logging prompts,
authorization headers or raw provider errors. A stopped request may already
have reached the provider, and retrying it can incur duplicate spend. An
uncertain terminal therefore requires explicit regeneration, not automatic
redispatch.

snapshot and fenced write surface first. Start with a bounded model-only
runner. Sequence output under the current claim and persist the watermark

and tool-call ID. Preserve the workflow execution ID as the receipt, even
if the model isolates or the output stream disconnects. Cancellation

issued child execution receipts. Qualify replay and cancellation before
enabling a second tool kind.

platform ceilings. The existing spike applies tighter workflow approvals

behavior at the pinned runtime, with hosted resource limits still requiring
separate qualification.

### Live-summary spike contract

Manual development enrollment requires the API hello gate and the same
`BIFROST_CLOUDFLARE_SUMMARY_ENDPOINT` on the API and private summary Worker.
The launcher opts in with `BIFROST_CLOUDFLARE_SUMMARY_WORKER`, which supplies
the service binding in its hosted config. The dedicated Worker config is
`summary-worker/cloudflare.config.ts`. Run the private Worker build from that directory. It uses no public hostname and disables
observability to keep command payloads out of traces. A missing binding
leaves workflow-only advertisement. Invalid provider configuration refuses
the summary before provider dispatch and leaves workflow handling available.

The API checks assignment metadata before reading the key. The admitted
slice is one unlinked OpenAI chat-completions profile pinned to the configured
HTTPS endpoint, with a resolved transport, no failover, and no explicit
reasoning setting. The API decrypts only that connection's key in a separate
read transaction before acquiring the dispatch and ownership locks. It never
runs transport discovery on the Cloudflare path. Rotation or revocation
affects the next key resolution.

The API sends the key on the authenticated control socket. The launcher
forwards it in memory via the named `SummaryProvider` RPC entrypoint. The
summary Worker exposes no fetch handler. The API WebSocket server must never
log frames at debug or trace level because command frames carry provider keys
and can already carry `engine_token`. The dedicated Worker pins the endpoint,
refuses redirects, and does not log request or response data. The provider
controls its response content, including any text it chooses to echo. The
configured endpoint and its operator must be trusted with both the key and
the transcript. The platform does not try to recognize encoded key material
in provider-controlled text.

The launcher advertises `agent.summarize@1` with `summary_claim_protocol: 1`.
The API starts its supervisor deadline at send time and issues a claim-bound
`cloudflare_summary` with a relative 30-second budget and a 16 MiB reservation.
The launcher computes its own deadline. Termination closes an RPC byte stream
that aborts the provider Worker's outbound fetch. The Worker also enforces its
own deadline and caps request and response bodies at 256 KiB and 64 KiB.
An already-issued request can still complete or incur charges upstream.

Opaque handles, receipts, and attempt states survive reconnect. Superseded live
routes receive a stop and hold their slot through terminal delivery. The API
holds its resolved provider for usage attribution and reads current eligible
profile metadata again on takeover without decrypting a key. If the assignment
can no longer attribute the result, settlement fails with an explicit summary
error. Missing optional token counts use Linux's existing zero defaults.

Each summary dispatch can attempt Cloudflare once. A definitive refusal
re-stages it for Linux and preserves queue age when the original owner knows
it. This bounds key resolution and route tombstones without a timer. The
Linux-only flag lives in the summary dispatch JSON payload. This spike uses
fresh disposable archives, so the withdrawn nullable-usage migration and its
flag rewrite are absent. An uncertain provider call requires explicit
regeneration.

For the disposable CT128 harness, run `phase5a.py prepare --summary` before
starting the isolated debug stack. Then run `phase5a.py run --summary
/path/to/generated-runtime.mjs` with Node 26 on PATH. Use the existing
[local harness instructions](../e2e/README.md) for stack ownership and cleanup.
The harness submits regeneration via the API, drops the first terminal ACK,
and requires one stub call and one persisted usage row across replay.

#### Runtime and admission

Use a bounded JavaScript agent loop in the trusted launcher. The API prepares
the authorized prompt, history, model, run mode, tool schema and budgets.
The launcher consumes model deltas, assembles a turn, requests the authorized
tool when needed and drives the continuation. Put provider-specific encoding
and decoding at the provider boundary. Reuse the API's existing prompt,
message, tool receipt and usage logic, extracting pure transformations where
needed. Keep Linux's child entrypoint, wire bytes and persisted behavior
as the baseline. The Workers loop needs neither a Python driver nor Redis.

Require the Cloudflare hello gate, a fixed HTTPS
`BIFROST_CLOUDFLARE_AGENT_ENDPOINT`, a nonempty JSON array of reviewed agent
UUIDs in `BIFROST_CLOUDFLARE_AGENT_FIXTURE_IDS`, and a launcher's
`agent_claim_protocol: "autonomous-v1"`. The first slice uses manually
enrolled launchers. Claim selection requires a queued, root run of an
allowlisted agent with a non-chat trigger, no conversation or output
schema, and room in a declared slot. Send-time checks must revalidate
the effective provider, agent, tools, caller, and budgets. Qualify zero tools
first and then one workflow tool and one continuation. Attachments,
knowledge, delegated agents, alternate providers, and chat stay on Linux.
The workflow pool admits the tool separately, so the tool fixture needs
independent workflow capacity while the agent holds its slot.

Autonomous runs persist AgentRunStep and AIUsage records instead of chat
conversation events. Chat requires a separate protocol and eligibility gate.
Its effective tool set includes built-in artifact tools when the profile
enables tool calling.

The API resolves the active admin-configured model profile and its connection
for each model turn. Qualify the same pinned OpenAI-compatible HTTPS
chat-completions transport as summaries. The API pins the selected profile
and model to the attempt and refuses a continuation if configuration changed.
Pass the key only in the authenticated per-turn command and across the
launcher's private provider service binding. Keep it out of DO storage,
snapshots, replay, logs, and TenantHost. The provider Worker enforces fixed
destination and model, rejects redirects, bounds bytes and time, and closes
its fetch when the launcher closes the cancellation stream. Run qualification
with a local stub using the same admin connection resolution path.

#### Attempt journal and stream

Use a PID-less route bound to the run UUID and the durable pool claim UUID.
The API records a claim-bound attempt and its absolute deadline before send.
Keep the assigned dispatch available for a proven pre-entry handback. Make
the transition to effect permission and the handback mutually exclusive
under the owner, claim and run locks. Before each provider call the API
durably records a single-use turn grant. A grant lost in transit is
conservatively treated as possibly used. No secrets go into the journal.

Sequence normalized deltas, completed turns and tool operations independently
of control socket sequence numbers. Use the same sequence and payload on
replay, with one unacknowledged batch per route for backpressure. Under the
current owner, pool claim and active run, PostgreSQL stores each accepted
batch and its watermark in the same transaction. Reject gaps and a
different payload at a committed sequence. Re-ACK an exact duplicate
without appending text, charging usage or dispatching again. Give committed
autonomous steps stable IDs and serve committed steps through the existing
run detail read. Partial model text lives in the attempt journal until a
complete response or an interrupted terminal is committed.

The first inventory after welcome advertises the opaque attempt and its
deadline. The replacement API owner checks the claim against the durable
cursor. A live launcher replays its outstanding request with the original
request ID and sequence, so the API can return its previous acknowledgement.
A launcher reset can recover the terminal journal but cannot recover an
open provider stream. Keep the route's slot through the terminal ACK, issued
after fenced settlement. Accept success only when all sequences through
the terminal watermark have committed.

#### Workflow receipts and cancellation

Send a workflow-tool request over the fenced control channel. Resolve the
binding from the snapshot, validate arguments, refresh the caller and use
the same agent, workflow and Solution authorization as Linux. Reconstruct
organization, acting and original users, lineage and inherited workspace
from the run on the API. Stage a normal Bifrost workflow execution so its
own lane and eligibility determine placement. Store the execution ID and
argument digest under a unique (run, claim, tool-call ID) in the same
transaction as workflow acceptance. A matching replay reads that receipt.
A conflicting replay is a protocol error. Hand off after commit, then
read the canonical execution outcome and use the existing tool result
shape. The launcher receives the receipt and bounded result, with no
workflow credential. A child can finish after its agent stops.

The Workers path shares bound-workflow authorization with
`execute_agent_workflow_tool` and calls `stage_workflow_run` in the
transaction that stores the receipt. A replay reads that receipt before
waiting for the result and checks the arguments against its stored digest.
Linux keeps its existing dispatch and result wait.

Cancellation uses the canonical AgentRun transition. Serialize it with
granting a turn, accepting a tool and settling the terminal. Reject later
grants and tool requests, send an idempotent terminate and close the
provider byte stream. Treat the absolute deadline the same way. Retain
partial text, known usage and child receipts. A granted model request may
still reach its destination and an accepted workflow may already have
effects. An abort or a stop reply does not establish either outcome.

| Attempt state | Required evidence and disposition |
| --- | --- |
| `not_started` | No granted provider turn, accepted tool or committed output. Return the original dispatch with its queue age and clear Workers eligibility for that dispatch. A cancelled run settles as cancelled. |
| `completed` | Observed terminal with all required deltas and tool receipts accepted. Commit the conventional success or failure once. |
| `uncertain` | A provider grant, accepted tool or committed output exists and the outcome cannot be established. Preserve partial evidence, mark the run failed or cancelled as appropriate, and forbid automatic redispatch. |

#### Chat outbox design

Keep chat on Linux until the outbox is qualified with real PostgreSQL,
Redis and the existing client replay path. The autonomous claim protocol
continues to exclude chat.

- Under the current run, claim and owner locks, commit each normalized
  chunk with the transcript mutation it represents. Use a unique key on
  `(run_id, claim_id, chunk_sequence)`, persist a safe event UUID and the
  sparse serialized `ChatStreamChunk`, and atomically advance the
  attempt cursor. Require contiguous sequence numbers and the same
  payload digest on replay. Reuse the same assistant message ID for
  message start, deltas, transcript writes and terminal projection. ACK
  the Worker after PostgreSQL commits, independently of publication.
- The API scheduler publishes the earliest unpublished chunk for a
  conversation using a short fenced lease. Allow one publisher per
  conversation and keep rows until they have a Redis receipt. An expired
  lease allows another publisher to reclaim the row. The publisher keeps
  the existing Redis channel, stream envelope, and conversation-wide
  sequence key, including for interleaved Linux events.
- Extend the existing Redis Lua operation to accept the stable UUID.
  For an existing UUID, return the stored conversation sequence without
  appending or publishing again. For a fresh UUID, allocate a
  conversation sequence, append to the stream, record the receipt and
  publish in the same Redis operation. Persist that sequence on the
  outbox row before allowing its receipt to expire. Keep receipts for
  unfinished rows even if the usual replay stream trims old entries.
  Validate stream and receipt key types before the script's first
  mutation. Reuse the current chat error redaction and client sequence
  semantics.
- An API crash before Redis publication leaves a committed pending row.
  A crash after Redis publication but before the PostgreSQL publish
  receipt leaves a row that returns the original Redis sequence on retry.
  A crash before the Worker receives the PostgreSQL ACK replays the
  existing outbox row. These recovery cases assume Redis retains its
  projection state. Qualify Redis restart, eviction and conversation
  reconstruction before enabling admission. The existing conversation
  reader and client replay cursor must converge after a projection reset.

`chat-outbox-protocol.test.mjs` models the three process-crash windows
and interleaving with the existing sequence allocator. Its durable stores
are in-memory fixtures. The production migration, publisher, Redis Lua
change and cross-process qualification remain separate work.
